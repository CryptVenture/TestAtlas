# TestAtlas Adapter Reference

> Status: living. Updated by Phase 14 Wave 5 (Plan 14-05).

TestAtlas ships **18 adapter packs** that translate the canonical
`.testatlas/commands/` source-of-truth into per-host renderable command files
(slash commands, prompts, workflows, rules, MCP prompts, etc.). Every adapter
is regenerated by `node scripts/assemble-adapter.js` from the same single
source set; the parity gate (`scripts/check-adapter-parity.js`) enforces
strict-mode coverage of every (command × adapter) obligation against the live
tree.

A command's rendered output path is determined by the adapter's `outputPattern` and `outputDir`:

- **Per-command-file adapters** (13 adapters: claude-code, opencode, kilocode, cursor, codex, gemini-cli, cline, windsurf, kiro, continue-dev, github-copilot, sourcegraph-amp, generic). Each source command emits one derived file. V1 flat commands land at the root of the adapter's outputDir; V2 categorized commands nest under matching `core/`, `explore/`, `council/` subdirs. Example:

  ```
  .testatlas/adapters/claude-code/.claude/commands/atlas-init.md       # flat V1
  .testatlas/adapters/claude-code/.claude/commands/core/atlas-status.md
  .testatlas/adapters/claude-code/.claude/commands/explore/atlas-explore-state.md
  .testatlas/adapters/claude-code/.claude/commands/council/atlas-council-domain-review.md
  ```

- **Multi-source / concatenated adapters** (5 adapters: aider, mcp, roo-code, zed, amazon-q). All commands are flattened into a single output file. The single file's adapter envelope carries an aggregate hash over `[V1 flat ∪ V2 categorized]` per-source hashes (sorted by absolute path). Examples:

  ```
  .testatlas/adapters/aider/CONVENTIONS.md
  .testatlas/adapters/roo-code/.roo/rules/atlas.md
  .testatlas/adapters/zed/.rules
  .testatlas/adapters/amazon-q/.amazonq/rules/atlas.md
  .testatlas/adapters/mcp/mcp-server-manifest.json
  ```

  The MCP manifest declares each command as a separate prompt (with V2 categorized commands carrying a `category-` prefix where needed for uniqueness — e.g., `atlas-core-init` distinct from flat `atlas-init`). Aider/roo-code/zed/amazon-q render an H2 section per command (≤7 lines each), each section pointing at the source path for full instructions.

## Persona / Council Strategy per Adapter

Three orchestration modes are supported:

- **subagent** — adapter spawns a separate sub-agent per persona (Task tool, plugin agent, custom-agent).
- **simulated** — single agent role-plays each persona sequentially (multi-pass).
- **prompt-pivot** — operator drives orchestration manually outside the agent (paste persona context per round).

| Adapter | Mode | Notes |
| --- | --- | --- |
| `claude-code` | subagent | `Task` tool. `.claude/agents/<persona>.md` (deferred — future plan) registers personas as Task targets. |
| `opencode` | subagent | Plugin-driven sub-agents; `agents/` dir holds persona definitions. |
| `kilocode` | subagent | Custom agents — `.kilocode/custom-agents/<persona>.md` (deferred). |
| `codex` | subagent | Sub-spawn via `/prompts:atlas-*` with persona context bundled. |
| `gemini-cli` | subagent | Multi-agent via TOML command chaining. |
| `cline` | subagent | Each council round is a separate workflow invocation. |
| `kiro` | subagent | Skill-chaining drives council rounds. |
| `sourcegraph-amp` | subagent | `.agents/commands/` chain. |
| `github-copilot` | subagent | Single-prompt with persona context bundle. |
| `cursor` | simulated | Multi-pass prompts within one chat. |
| `windsurf` | simulated | Multi-pass within one workflow chain. |
| `continue-dev` | simulated | Multi-pass slash invocations. |
| `aider` | simulated | Multi-pass within a single Aider session. |
| `roo-code` | simulated | Multi-pass within one chat. |
| `zed` | simulated | Multi-pass within one Zed Assistant chat. |
| `amazon-q` | simulated | Multi-pass. |
| `generic` | prompt-pivot | Operator pastes persona context manually each round. |
| `mcp` | prompt-pivot | MCP `prompts/get` returns each council command body; operator orchestrates rounds in their MCP client. |

## Regeneration Workflow

1. Edit a source command at `.testatlas/commands/<name>.md` or `.testatlas/commands/<category>/<name>.md`.
2. Run `node scripts/assemble-adapter.js` to regenerate every adapter (or `--adapter <name>` for one).
3. Run `node scripts/assemble-adapter.js --check` to confirm zero drift.
4. Run `node scripts/check-adapter-parity.js` for the strict-mode parity gate.
5. Commit the source change AND the regenerated adapter outputs together.

The parity gate hashes each source file and embeds the hash in the derived
file's `<!-- TESTATLAS:GENERATED:START -->` marker. Any source mutation
without regen is detected as `hash-mismatch`; any hand-edit to a derived file
is detected as `hand-edit`; any deleted derived file is `missing`; any
malformed envelope is `no-marker`.
